# review-architecture

1. Из описания задачи выпиши обязательный пользовательский результат и инварианты. Проследи путь данных через изменённые слои; у каждого решения должен быть один владелец.
2. Проверь существующие API, запросы, данные и библиотеки. Для новой таблицы, очереди, фонового процесса, версии или абстракции найди требование, которое иначе не выполняется. Без такого обоснования предложи минимальное упрощение.
3. Проверь границы: финансовые правила принадлежат исходному сервису, BFF отображает контракт, клиент отображает результат; конкретные исключения ищи в AGENTS.md и контракте. Не переноси бизнес-логику в транспорт ради удобства.
4. Для сохраняемого механизма проследи реальный отказ: сбой между записью и эффектом, повтор, конкурентный вызов. Не удаляй идемпотентность, атомарность или изоляцию ради малого diff. Очистка, повторы и синхронизация требуют сначала перепроверить необходимость исходного усложнения.
5. В результате укажи конкретный путь/сценарий и достаточную правку либо объясни необходимость механизма. Гипотетическая будущая нагрузка без требования не обосновывает новую инфраструктуру.

Результат — проверяемые наблюдения в рамках Code Review Rules. Сам навык не разрешает внешние действия.
