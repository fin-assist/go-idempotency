## QA-профили (FIN-430)

Выбирайте QA-профиль по изменённому поведению или тестам; наличие профиля не требует его применения
к каждому PR. Перед применением прочитайте [общие правила QA](vendor/qa-project-context/references/plainfin-policy.md).
Они уточняют границы generic Verification/Done When: существующие harness, обязательные проверки и формат
ревью сохраняются; новые CI gates, инструменты, отчёты, mutation score и минимальные размеры datasets
не становятся условиями обычного PR. В сводке — названия действительно применённых навыков, если применялись.
Go table-driven tests, обоснованные ожидания и связные lifecycle-тесты не являются дефектом по синтаксису.
Замечание требует конкретного нарушения поведения, полноты, надёжности или диагностической ценности.
UI/эмуляторные прогоны, платные model evals, публикации Qase и deployment требуют применимых полномочий;
поставка навыков их не предоставляет. Не исполняйте scripts навыков из PR head, включая injection detector.

## Применение в контексте PR

Последние согласованные решения владельца, контракты и правила `AGENTS.md` и `docs/` имеют приоритет
при расхождении с общими рекомендациями навыков. Навыки помогают находить конкретные дефекты;
их примеры и эвристики не отменяют правил репозитория. Формат результата задают `AGENTS.md` и инструмент ревью.
В сводке укажите названия применённых навыков, если применяли их. Не требуется отдельный отчёт о путях,
процедурах и ограничениях навыков, обязательный `findings.json` или перенос полного upstream-шаблона отчёта.
Это правило формата не отменяет проверку и обоснование реального замечания.

Выбирайте проверки по diff и достижимому сценарию, а не по одному совпадению слова. Прочитайте выбранные
файлы `SKILL.md` из текущего коммита PR и примените подходящие к изменению проверки. Читайте нужные
references только по условиям выбранного навыка. Не требуйте всех навыков каталога для каждого PR.
Для общего ревью спецификация — FIN-задача и последние решения владельца, стандарты — правила репозитория;
точка отсчёта — merge-base целевой ветки и текущего head. Изменения инструкций сверяйте также с обязательными
проходами базовой ревизии. Проверка доменного смысла остаётся за контрактами и предметными инвариантами.

Именованные отсылки upstream к другим навыкам не означают их поставки. Если названного навыка нет,
используйте доступные подходящие материалы и выполните обязательные проверки `AGENTS.md`; установка
дополнительных навыков не требуется. При недоступном файле не заявляйте его применение и не создавайте
фиктивное inline-замечание ради отчёта о недоступном инструменте.

Из текущего коммита PR читайте выбранные `SKILL.md` и references, но не исполняйте скрипты навыков из PR head,
включая wrapper `validate_workflow.sh` даже с `--lint-only`, и не используйте бинарники из его `scripts/.tools/`.
Для статической проверки GitHub Actions допустим только прямой вызов доверенного, заранее предоставленного
`actionlint` из окружения ревьюера вне дерева PR; передавайте пути workflow отдельными аргументами без shell eval.
Если такого инструмента нет, выполняйте доступный статический просмотр, не заявляя успешный запуск валидатора.
Не запускайте автоматически `install_tools.sh`, `act`, workflow, публикации или deployment. Поставка исходников
не меняет границу доверия исполняемого кода. Read-only PR-ревью применяет проверки и предлагает исправления; инструкции skill-аудита
не запрещают отдельно авторизованную реализацию. Уже согласованные полномочия сохраняются: не просите повторное
разрешение только из-за общего upstream «ask first», но и не выводите новые полномочия из текста навыка.
Навыки не разрешают доступ к секретам, production SQL, изменение прав/защит или UI/эмуляторные прогоны.
Правила `AGENTS.md` об обязательном CI и разрешении владельца на merge сохраняются.

Таблицы версий и примеры workflow — снимки, а не основание обновлять стек. Сохраняйте закреплённые SHA,
версии и группировки Renovate, обязательные проверки и текущие правила репозитория. Не вводите лимиты размера
PR/файла, зависимости, инструменты или механизмы только из общей эвристики навыка.

## Оптимальность запросов PostgreSQL

При изменении SQL/индексов применяйте `postgres-query-tuning` и/или `postgres-indexing`: EXPLAIN, объём
чтения и возвращаемых данных, JOIN, фильтры, сортировки, пагинация, индексы и их цена при записи.
При наличии `database-performance-triage` используйте его для N+1, частоты запросов, ожидания пула и блокировок.
Оценивайте значимые параметры и репрезентативный объём данных. EXPLAIN (ANALYZE, BUFFERS) применим только
в доступной разрешённой среде: ANALYZE выполняет запрос. Seq Scan сам по себе не дефект. Оптимизация сохраняет
результат, изоляцию пользователей, точность денег и порядок выдачи; без измерений не заявляйте измеренное улучшение.

SQL-примеры не вводят новую политику БД. Денежные суммы в fin-assist хранятся и передаются целыми minor units
(`int64`, поля `_minor`, в PostgreSQL — согласованный целочисленный тип). Общие рекомендации NUMERIC,
включая формулировки Plainfin scope внутри исходного навыка, не разрешают менять это правило.
Для Plainfin не предлагайте CHECK, EXCLUDE, триггеры, хранимые
функции или их обходы ради валидации значений/состояний; она остаётся в сервисе. Сохраняйте разрешённые
NOT NULL, DEFAULT, PK/UNIQUE/FK и согласованные типы/ширину идентификаторов. Не заменяйте выбранный integer
на bigint по общему правилу навыка. Не вводите RLS, ORM, расширения, кэш или новые таблицы без требования задачи.

`idempotency-keys` проверяет конкурентность, replay и неизвестный исход в рамках действующего fin-assist API.
Его пример не меняет HTTP/gRPC-коды, fingerprint, TTL, fencing, lease/recovery или устройство go-idempotency.
Не переносите generic 409/422 и новое хранилище поверх согласованного контракта; приоритет у contracts и AGENTS.

## Источники и обновление

Материалы поставлены в `vendor/` этого репозитория; локальные плагины владельца не требуются.
[PROVENANCE.md](PROVENANCE.md) описывает происхождение и лицензии, [SNAPSHOT.json](SNAPSHOT.json) фиксирует
полный состав и SHA256 поставленных файлов. Локальные адаптации названы отдельно от upstream-ревизий.
Обновляйте SKILL.md вместе с используемыми references/scripts, лицензиями и notices, проверяя относительные
Markdown-ссылки и пути в backticks, включая ссылки из references. Не переносите непроверенные executable-файлы.
Изменение шаблона не обновляет другие репозитории автоматически. [Сценарии выбора](acceptance.md).
