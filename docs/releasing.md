# Версии и выпуск

Правила для всех Go-библиотек «Понятных финансов» ([FIN-118](https://finassist.youtrack.cloud/issue/FIN-118)): `go-idempotency`, `go-outbox`, `go-tombstone`, `go-identity` и следующих, созданных из `fin-assist/go-library-template`. Сервис закрепляет версию библиотеки в своём `go.mod` и получает новые версии PR-ом Renovate.

## Номер версии

Теги [semver](https://semver.org/lang/ru/) `vX.Y.Z` на коммите `main`, без префиксов и суффиксов (`-rc`, `-beta` не используются).

**До первого прода — `v0.MINOR.PATCH`.** В Go версия `v0` не обещает совместимости, поэтому:

| Изменение | Версия |
|---|---|
| Несовместимое (см. ниже) | новый MINOR: `v0.3.1` → `v0.4.0` |
| Новая возможность без несовместимостей | новый MINOR |
| Исправление, внутреннее изменение, документация без изменения API и поведения | новый PATCH: `v0.3.1` → `v0.3.2` |

**`v1.0.0`** — когда библиотека работает в проде хотя бы в одном сервисе; решение владельца, отдельной задачей. С `v1` несовместимое изменение возможно только как `v2` с новым путём модуля (`github.com/fin-assist/go-outbox/v2`), поэтому его избегают: новое добавляется рядом, старое объявляется `Deprecated:` и удаляется в следующем major.

## Что считается несовместимым

Несовместимо всё, после чего сервис, обновивший библиотеку без правок, перестаёт собираться или начинает вести себя иначе:

- **API Go**: удалено или переименовано экспортируемое имя, изменилась сигнатура функции или метода, в интерфейс добавлен метод, в структуру — обязательное поле без нулевого значения по умолчанию. Это находит `gorelease` (job `api` в CI, `make api`).
- **Поведение, на которое опирается сервис**: код ошибки (`reason`) или gRPC-статус для того же случая, metadata ошибки, значение по умолчанию (TTL, таймаут, размер пачки), семантика повтора, порядок интерцепторов, который библиотека требует.
- **Наблюдаемость**: имя метрики, её метки и единицы — на них завязаны алерты и дашборды.
- **Схема**: миграция, после которой сервису нужно поменять свой код или свои миграции; удаление или переименование столбца, которым сервис пользуется напрямую.
- **Зависимости**: новая минимальная версия Go, мажорная версия `contracts/gen/go` или другой зависимости, которую сервис тоже импортирует.

Новое необязательное поле опций, новая функция, новый вариант ошибки в месте, где сервис уже обрабатывает «любую другую», — совместимо.

## CHANGELOG

`CHANGELOG.md` в формате [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), по-русски. Каждый PR библиотеки сразу добавляет строку с ключом FIN (если он есть) в раздел `## [Unreleased]`, включая изменения документации, тестов и CI. Запись входит в тот же PR, а не откладывается до выпуска. Используется одна из групп:

- `### Несовместимо` — что сломается и что сервису сделать при обновлении;
- `### Добавлено`, `### Изменено`, `### Исправлено`, `### Удалено`.

Для внутренних правок запись кратко описывает результат и не приписывает им изменение runtime или API. Исключение — полностью ботские PR Renovate, которые меняют только зависимости (FIN-211): они строку не добавляют, иначе человеческий коммит переведёт PR на ручное сопровождение. PR выпуска переносит накопленные записи в секцию версии по шагу 1 ниже и проверяет весь `git diff <последний тег> -- go.mod`:

- **Несовместимое** по «Что считается несовместимым» → «Зависимости» (повышенная директива `go`, мажорная версия зависимости, которую сервисы тоже импортируют) — по всему diff, от кого бы оно ни пришло. У каждого такого изменения должна быть строка в «Несовместимо»: из его PR или добавленная PR выпуска.
- **Остальное** — в «Изменено» только изменения от PR Renovate, ещё не описанные строками `[Unreleased]`: изменения обычных FIN PR уже описаны их строками. Авторство изменения видно в `git log -p <последний тег>..HEAD -- go.mod`.

Формат проверяет CI (`scripts/changelog.py check`).

## Выпуск

1. **PR выпуска** (`tooling/release-vX.Y.Z`, заголовок `FIN-<n> Выпуск vX.Y.Z`): раздел `[Unreleased]` переименовывается в `## [vX.Y.Z] — ГГГГ-ММ-ДД`, сверху — пустой `[Unreleased]`; по всему `git diff <последний тег> -- go.mod` проверяются несовместимые изменения зависимостей (строка в «Несовместимо» у каждого), а в «Изменено» добавляются ещё не описанные изменения от PR Renovate (см. «CHANGELOG»). Job `api` проверяет, что `gorelease` принимает номер: несовместимое изменение с новым PATCH CI не пропустит. Локально — `make release-check VERSION=vX.Y.Z`.
2. Владелец мёржит PR и ставит тег на коммит слияния: `git tag vX.Y.Z && git push origin vX.Y.Z`. Агент тег не ставит.
3. Workflow `Release` проверяет тег (формат, путь модуля для `v2+`, коммит на `main`, раздел в CHANGELOG) и создаёт GitHub Release с текстом раздела.
4. Renovate открывает PR обновления в каждом сервисе, который использует библиотеку (см. ниже).

Выпущенный тег не переставляется и не удаляется: прокси Go и `go.sum` сервисов уже запомнили его содержимое. Ошибка в выпуске — новый PATCH; совсем негодная версия — директива `retract` в `go.mod` следующего выпуска.

### Если тег опубликован до PR выпуска

Сначала проверьте сам тег, доступность модуля и GitHub Release: опубликованный модуль и оформление GitHub Release — разные результаты. Создание GitHub Release вручную не исправляет CHANGELOG и не делает упавший workflow успешным.

В FIN-227 теги `v0.1.0`–`v0.4.0` уже опубликованы, а записи оставались в `Unreleased`. История восстановлена в следующем PR выпуска `v0.4.1`: даты взяты из опубликованных GitHub Releases, записи распределены по изменениям между тегами. Этот PATCH исправляет только оформление и документацию; код и миграции совпадают с `v0.4.0`.

Порядок восстановления:

1. Не меняйте существующие теги. В отдельном PR восстановите разделы прежних версий и добавьте следующий PATCH с описанием исправления; сверху оставьте пустой `Unreleased`.
2. Выполните `make release-check VERSION=v0.4.1` и проверьте отчёт CI `api`. Рекомендация/подтверждение номера в summary `gorelease` и отсутствие диагностик зависимостей — разные результаты: известная диагностика отозванной ADAL ведётся в FIN-213 и не должна описываться как успешный raw `gorelease`.
3. Владелец мёржит PR, дожидается успешного CI и ставит новый тег на проверенный коммит слияния. Убедитесь, что новый workflow `Release` завершился успешно и GitHub Release содержит текст нового раздела CHANGELOG.

Повтор старых запусков для `v0.2.0`, `v0.3.0` или `v0.4.0` не поможет: workflow читает CHANGELOG из неизменного коммита тега, а не из обновлённого `main`. Их исторический статус failure сохраняется. Для этих версий GitHub Releases уже существуют; создавать дубликаты не требуется. Если оформления у опубликованного тега нет, его можно восстановить отдельно с проверенными notes, не перемещая тег; это не заменяет корректный PR перед следующим тегом.

### Повтор публикации существующего выпуска

Workflow `Release` можно запустить из `main` вручную с параметром `tag`, например `v0.4.1` (Actions → Release → Run workflow). Он проверяет существующий тег, его принадлежность `main`, путь модуля и CHANGELOG именно из коммита тега. Тег не создаётся и не меняется. Скрипты проверки тега и публикации берутся из `main`, поэтому исправление публикации работает и для старого тега с корректным CHANGELOG.

Если GitHub Release уже создан вручную или предыдущим запуском, workflow обновляет его title и notes по CHANGELOG вместо повторного создания. Черновик, prerelease, несовпавший тег, неполный ответ GitHub или ошибка обновления не считаются успехом. Для `v0.4.1` ручной запуск заменит автоматически сгенерированные notes подготовленным разделом FIN-227. Для старых тегов без раздела CHANGELOG проверка по-прежнему завершится ошибкой.

Тег ставится после успешного post-merge CI. Если поставить его во время job `api`, checkout мог ещё не видеть тег, а `gorelease` уже обнаружит опубликованную версию и откажет с `already exists`. В таком случае после стабилизации тега повторяют упавший job; существующий тег не меняют.

## Миграции

Миграции библиотеки — отдельный источник golang-migrate со своей таблицей версий `<библиотека>_schema_migrations` ([FIN-115](https://finassist.youtrack.cloud/issue/FIN-115), `docs/migrations.md` в `fin-assist/go-service-template`). Сервис применяет их командой `migrate up` до своих.

- Выпущенный файл миграции не меняется: он уже применён в базах сервисов. Изменение — новым файлом (CI запрещает правку и удаление существующих).
- Каждая миграция проходит «вверх → вниз → вверх» (`migrations_test.go`) и squawk.
- Несовместимое изменение схемы — в два выпуска, как в сервисе: «добавить» в одном, «удалить» в следующем, когда все сервисы перешли на код без старого столбца. Между ними — запись в CHANGELOG, что сервисам нужно обновиться.
- Миграции сервиса могут ссылаться на таблицы библиотеки, миграции библиотеки на таблицы сервиса — нет.

## Как сервисы получают обновления

**Renovate** (GitHub App на организации, режим Interactive) по `renovate.json` в каждом репозитории:

- `github.com/fin-assist/*` (библиотеки и `contracts/gen/go`) — отдельный PR на каждый модуль сразу после тега, с `go mod tidy`;
- остальные зависимости (Go-модули, GitHub Actions, образы) — один сгруппированный PR в неделю, в понедельник утром;
- версию Go (`go`, `toolchain`) Renovate не трогает — её поднимают вручную вместе с CI.

PR Renovate проходит CI сервиса. После активации FIN-211 полностью ботское совместимое обновление сливается контроллером по [политике Renovate](renovate-policy.md). При несовместимом обновлении владелец или агент исправляет сервис по записи «Несовместимо» в CHANGELOG: человеческий коммит в ещё открытой ветке Renovate переводит PR на ручное сопровождение и блокирует автоматические повтор, закрытие и merge. Если контроллер уже закрыл PR после повторного падения, правки делаются отдельным PR с задачей YouTrack; повтор исходного обновления доступен через Dependency Dashboard по политике. Ветки `renovate/…` — исключение из правила имён; задача YouTrack не нужна, пока PR меняет только зависимости.

## Доступ к модулям

Все репозитории `fin-assist` сейчас публичные: модули берутся из git напрямую (`GOPRIVATE=github.com/fin-assist/*`), токен не нужен. Если библиотека станет приватной:

- CI — секрет `GO_MODULES_TOKEN` с чтением репозиториев `fin-assist` (шаг «Access to private modules» уже есть в workflow);
- `docker build` сервиса — секрет `netrc`;
- локально — `git config --global url."https://x-access-token:<token>@github.com/fin-assist/".insteadOf "https://github.com/fin-assist/"`;
- Renovate видит приватные репозитории организации через своё GitHub App, если оно установлено на них.
